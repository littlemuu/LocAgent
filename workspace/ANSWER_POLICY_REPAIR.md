## 失败证据

v2 首题基础组第 3 次回包是完整的 `finish`，`finish_reason=tool_calls`，参数 JSON 可解析，正文 1527 字符、输出 542 tokens，远未触及 2048 输出上限。旧本地校验仅因正文超过 1200 字符而拒绝，其他字段与源码成员约束通过。直接原因是我们把简洁表达要求做成了成功条件，不能归因于模型无法完成任务或检索效果。

原始三次交换已复制为不含认证头或密钥的回归夹具。旧账本、失败状态、回包和费用记录不改写，旧答案不回溯记为成功或纳入质量评分。

## 新配置

| 项目 | v3 行为 |
| --- | --- |
| 简洁目标 | 提示“约 1200 字符”，明确是风格建议，不是硬限制；保留回答所需证据 |
| `answer` schema | 必需的 string，无字符 `maxLength`；完整内容不裁剪、不缩写、不另调模型修复 |
| 结构与来源 | 仍严格校验字段、类型、最多五个文件/实体、唯一性及源码成员 |
| 模型输出 | 保持每次 2048 tokens；`finish_reason=length` 仍拒绝并停止 |
| 原始 HTTP 回包 | 保持 65536 bytes（64 KiB）上限；超限保存有限原始前缀并标记 incomplete，不将其当成有效回答 |
| 离线响应 | 从 8 KiB 同步到现有真实传输的 64 KiB，以免离线验证另有更小的隐藏限制 |
| 额度与失败 | 保持 4 请求/组、8/题、48/套；已知 usage 结算，未知用量保留预留；异常停止全套，无自动重试 |

字符数不再代替 token 或字节预算。系统提示、wire schema、核心验证与 SDK 路径一致；两个分组采用相同约束。真实 HTTP 传输容量和输出 token 上限均未增加。

## 异常报告补充修复

超大回包测试发现：执行器已正确停机并保留未知费用预留，但事后审计把不完整 body 当作 JSON 解析，导致报告生成失败。现在仍先核对原始字节 hash，对未结算/不完整/缺失 receipt 记录证据缺口，不尝试将其解析成模型行为；异常工具参数也记录为不可验证。缺失证据不再被表述为“未选择检索”。

这不吞掉账本篡改错误：请求/回包哈希和计划绑定检查仍严格保留。新执行 manifest 也绑定审计模块 hash，保证冻结报告逻辑。首轮超大回包失败日志及模拟账本保留，修复后使用新模拟目录验收。
