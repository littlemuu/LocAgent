# 继续研究未选检索：选择当时的证据状态

2026-11-13（北京时间）。目前最有证据支持的解释是：**模型按任务和已有线索分配工具；SQLGlot修复后的普通读取已经完成了实体检索最容易补足的工作。工具说明可能进一步引导“已有文件就读文件”，但尚不能确定它对选择的因果影响。**

本轮只分析已有真实收发与SDK事件，没有新增模型请求、没有执行目标仓库代码，也没有读取密钥。新增逐轮审计与一份单变量对照草案；生产工具、授权及历史结果未改。

## 新证据一：同一工具定义曾被自主选择

回查全部现有生产命名空间的已保存响应，找到两条正例，并重新验证模型选择→SDK执行→证据进入下一请求→正常finish的完整链：

| 正例 | 实际查询 | 首次选择 | 观察JSON字节数 | 核验 |
|---|---|---|---:|---|
| 自写webhook样例 | `webhook delivery retry` | 第1轮，auto | 1,642 | 成功，证据进入第2请求，正常终答 |
| 六题开发集的文档权限样例 | `share token access check document` | 第1轮，auto | 2,048 | 同上 |

两条正例与当前SQLGlot的 **locagent_retrieve完整工具定义（名称、说明、参数schema）逐项相同**，工具名称及顺序也相同；请求模型名均deepseek-flash、温度0、非思考。对应题目和系统提示不同，read_file接口也经过修改；模型别名不是不可变版本，因此它们是能力反例，不是因果配对实验。

可以排除这些绝对说法：

- “这个模型不会调用LocAgent。”
- “这个工具名/schema在现有接入里始终不可调用。”
- “这份说明或第四个工具的位置使它绝不选择检索。”

仍不能排除：说明或排序降低了某些任务上的选择概率。两条正例都在首次调查用概念词查询；这与检索作为起步发现工具的使用方式相容，但不足以归纳模型固定策略。没有用正例的数量计算跨批次成功率，各批次题目与协议不一致。

## 新证据二：修复前后不是同一种“没用检索”

审计两题旧批次及SQLGlot读取修复后批次的3个检索可用组，共9个调查请求。9/9均提供相同检索工具并允许auto，实际调用0。最后一轮只允许finish，不纳入机会数。

下表描述**发出该轮模型请求时已经收到的证据**，不是把本轮新生成的工具调用当成旧知识。

| 轨迹 | 第1轮 | 第2轮 | 第3轮 |
|---|---|---|---|
| Loguru旧批次 | 无参考符号/正文 | 无参考符号/正文；见过文件路径 | 仍无参考符号/正文 |
| SQLGlot修复前 | 无参考符号/正文 | **已见参考符号，未见正文** | **已见参考符号，未见正文** |
| SQLGlot修复后 | 无参考符号/正文 | 尚未见完整参考符号；已有搜索命中的位置 | **参考符号和完整19行正文均已收到** |

- 修复前SQLGlot第2/3轮分别还剩14/12次调查调用、12,277/7,434 bytes；已见短符号的完整检索页仅1,244 bytes。两次存在明确的“已知名、缺正文、可查且装得下”机会，模型选择了read_file/search_text；旧read_file的offset混淆导致补证失败。
- 修复后第3轮剩12次调查调用、8,990 bytes，检索仍可用；但上一轮正确按行读取已经交付全部目标正文。**本条自然轨迹没有出现“已知参考符号而正文仍缺失”的开放调查状态。** 因而不能拿它来直接验证模型是否会在这个状态选择实体检索。
- 这只判断指定参考函数的正文覆盖，不是判断整道题已解决：周边函数、Snowflake特定逻辑和回答中的推断仍可能需要更多证据。

因此，修复后0调用与“基本工具已满足当前读取需求”相容；它并不复现修复前放弃补正文的同一种机会。不能据此声称模型判断了检索的收益，也不能声称读取修复因果导致了0调用——前后本来都是0，且实际轨迹不同。

## 当前各解释的证据地位

| 解释 | 当前判断 |
|---|---|
| 工具没暴露或没注册 | 这些调查轮次的wire证据反驳；两条成功正例也反驳普遍接入失败 |
| 调用数或证据预算硬阻断 | SQLGlot已见符号机会中不成立；有限调查轮数是否影响偏好仍未知 |
| 新SQLGlot中基础工具已完成读取任务 | 有直接证据；目标名可用时完整正文也已到达。对“为什么选择”的解释仍为推断 |
| 检索说明把模型引向普通工具 | 可检验假说。说明确有“read_file for a known file”；没有专门说明“已知函数名但缺完整正文”的分工。两条正例证明不是绝对禁用 |
| Loguru的任务措辞/发现能力不匹配 | 题目要求单测，真实轨迹追查测试；ID检索又排除测试、自然词未命中目标。事实支持任务/能力不匹配，但模型没实际看过这些离线空结果，不能说它因空结果放弃 |
| 模型看到检索大回包后不再使用 | 这三组真实检索调用为0，没有发生这种反馈；离线大结果不是模型经历 |
| 256字符限制导致这次不选 | 是接口说明缺口，但没有真实过长检索尝试，不是已观察到的阻断 |
| 工具名称陌生、训练偏好、位置效应 | 尚无辨识这些因素的对照；不能当作事实解释 |

## 已准备的最小区分实验（离线草案，未执行）

继续反复重跑整题，可能只会再得到一次0调用，却不能区分原因。更直接的诊断是固定一个“有已见符号、缺正文”的决策点，仅改变工具说明。

材料取自旧SQLGlot第2请求：第1轮只有普通搜索，没有发生错误offset读取。两份草案均换入当前修复后的基础工具和系统提示，其余问题、搜索证据、预算、模型参数、工具名称及顺序保持一致。它是**人工构造的历史状态重放**，不是新读取接口下自然产生的轨迹，不用于完整Agent评分。

- 对照：当前说明原文。
- 候选：只在现有分工句里明确已知符号取正文的用途：

> Use search_text for literal text inside source, and read_file for a known file or line range. If you know a symbol name but have not read its complete body, this tool can return that entity source without choosing line bounds.

其余关于实体ID BM25、非正文/语义检索、不遍历调用图、证据相关性和分页的限制均保留。没有添加强制使用要求、改名、换顺序、改查询长度或增加调查预算。

离线JSON比较确认两份请求只有 **`/tools/3/function/description`** 不同。两者仍为auto；不调用任何传输或创建授权。

若后续要验证，主指标应是同一状态下的首次响应是否自主选择locagent_retrieve；保存不选择、错误和所有重复样本，不做挑选后补跑。一次配对只能提供小样本观察，多次随机顺序对照才有较好的稳定性信息。仅生成下一步响应不验证工具执行、最终答案或检索收益；要测这些需另立方案。真实调用前必须另报样本数、发送范围、价格与总上限并获批。

**结果解释也预先区分：**候选更常选，只支持该构造状态下说明影响选择；两者都不选不能证明模型不会检索；两者都选说明说明未必是必要因素；任何结果都不能直接推广到Loguru或完整自然任务。
