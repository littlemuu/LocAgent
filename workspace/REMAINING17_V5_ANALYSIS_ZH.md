# 开发结果分析：整体流程、检索贡献与证据预算

结论：这批结果支持继续沿用 OpenHands 作为当前开发底座，并优先改善证据获取效率；尚不能把系统优势归因于 LocAgent 检索。当前主要问题已从“交不出合法终答”转向“有限证据预算里能否拿到正确函数”。这是对本次已曝光开发题的判断。

## 1. 观察到的系统优势有多大

最新 17 道同版本行为的配对结果：

|指标|原生适配组|OpenHands 组|
|---|---:|---:|
|完成终答|17/17|17/17|
|Hit@1|10/17（58.8%）|13/17（76.5%）|
|Hit@5|12/17（70.6%）|15/17（88.2%）|
|平均 Recall@5|67.6%|81.4%|
|请求数|59|65|
|输入 token|379,017|299,993|
|输出 token|14,076|15,178|

Hit@5 是“前五个候选中至少命中一个冻结参考实体”，不是所有实体都定位正确。逐题配对为：12 题都命中、3 题仅 OpenHands 命中、0 题仅原生命中、2 题都漏检。OpenHands 多命中的题为 SQLGlot #3901、#4366、xCDAT #689。优势来自三道具体题，不能把 17.6 个百分点当成稳定泛化收益。

原 19 道 v4 完成题的 Hit@5 为原生 11/19、OpenHands 10/19；不能把它与这批 12/17、15/17 直接比较成版本提升，因为题目组成不同。当前全 37 题有完成记录，但 19 题是 v4，18 题是 v5（含 Sisyphus）；不合并成统一版本成绩。本次 13/17 来自 SQLGlot，也存在仓库相关性和分布偏斜。

加上 Sisyphus，新协议在 18 道开发题的 36 组真实执行中均正常收尾，这是流程稳定性的正面证据；不保证未来不会再遇到格式错误，也不表明定位全部正确。

## 2. 检索开始被自主选择，但“调用了”不等于“带来命中”

SDK 在 6/17 题自主调用了 LocAgent，共 7 次；没有强制调用。直接检查实际发送给模型的工具消息，而非只看工具审计中的累计字节数：

|题目|LocAgent 实际返回|后续可见轨迹与结论|
|---|---|---|
|luigi #3324|完整精确匹配 `CopyToTable.copy`，工具消息约 1.4 KB|可靠提供目标函数；两组都命中，因此没有证明净增益|
|SQLGlot #3901|查询 `_parse_apply`，返回 `No locations found.`，49 字节|普通 search_text/read_file 后覆盖 `_parse_join` 正文 3229–3287 行，SDK 命中；不能算检索直接找到答案|
|SQLGlot #4366|`duckdb struct_sql` 首屏返回通用 `Generator.struct_sql` 和 DuckDB 类，4 KB；没有目标 `_struct_sql`|后续按行读取 duckdb.py 154–178 行完整目标正文并命中；不能算检索直接命中|
|SQLGlot #4369|`Expression.or_` 返回模块函数 or_ 在前、类方法在后；`Expression.is_leaf` 返回目标及大量 Expression 类内容；共 8 KB|提供了真实符号和实现，但排序/长类内容消耗明显。两组都命中，SDK 首个候选排名更好；最终因果贡献未知|
|SQLGlot #4526|精确目标 `Step.from_expression` 的首屏，4 KB，有续页|后续按行读取关键实现；两组都命中，SDK 3 请求、原生 4 请求。可以进一步验证取证步数，但单次不足以定因果|
|xCDAT #689|climatology 首屏主要为签名与长 docstring，4 KB，没有六个参考实体的完整 ID|随后读取与搜索 helper，SDK 命中 `_group_average`、`departures`。该首屏可能提供入口，尚未证明不可替代|

7 次返回里有 5 次达到 4,096 字节分页大小并给出 next_offset，这 5 次都没有经 LocAgent offset 续页，模型改用其他工具。只有 3 次返回文本直接包含至少一个冻结参考实体完整 ID；这是事后文本证据检查，不是把 gold 用于查询，也不是对整体检索召回率的估计。

新增命中的三题都调用过检索，但 #3901 是空结果，#4366 首屏未含目标；所以“6 题调用检索且都命中”不能作为检索效果结论。调用选择本身与题目线索有关，而且工具组合、上下文、预算消耗均不同。

## 3. 最明显的工程线索是证据预算消耗

原生组 14/17 题精确耗尽 14,336 字节证据额度，其中 9 题只发了 3 次模型请求就被迫收尾；SDK 3/17 题达到控制器的证据关闭阈值（14,272 字节），其余可以保留更多调查空间或自主提前结束。

源码证据累计字节合计：原生 236,618，SDK 182,222。SDK 请求多 6 次，输入 token 却少 20.85%。较少请求不等于更高效，可能是更早耗尽证据。

原生工具消息中，13 次目录/结构浏览累计约 50 KB；大量条目带导航及合法终答格式说明。44 次实际返回内容的 search_code_snippets 中 40 次有后续页面，但实际 read_tool_output 只有 3 次。这个差距只是“分页很多、续读很少”的观察，不表明每一页都该继续读，也不能据此断言模型忽略提示。

工具消息的 JSON 封装/转义也占预算；文本自身还可能包含重复说明、类文档和无关候选。这是格式层与检索层共同的问题。下一步应测量“同样字节额度能容纳多少与问题相关的实现”，而非先把轮数/预算翻倍。现有 source_bytes 规则仍按原口径保留，不能为提高分数临时把开销移出预算。

## 4. 两道共同漏检告诉我们什么

- SQLGlot #4415：两组聚焦 `_parse_table_parts` / TABLE 相关线索，冻结目标为 `Parser._parse_column_ops`（5096–5146 行）。实际模型可见工具输出连 `_parse_column_ops` 这个叶子名都未出现；SDK 主要读的是 parser.py 3600–3695 行和 Snowflake 的 table parts。更像证据路线停在表名解析，没有走到表达式/列操作分支；不能直接判定模型“看到了却不会推理”。
- SQLGlot #4524：两组关注 LEVEL/CONNECT BY、校验报错及星号展开。冻结目标为 `Resolver.get_source_columns`（859–903 行），模型可见工具输出没有该叶子名；SDK 读到 1–130、556–594 等区域，未覆盖目标实现。可检验的缺口是如何从已见 Resolver/列解析线索继续追踪，而不是向查询偷加标准答案。

原始标签还存在语义审查边界：#3167/#4369/#4523 有潜在漏标的被编辑函数线索；xCDAT 有六个 gold，但只允许最多五个预测，Recall@5 理论最高 5/6，且模型命中的只是其中部分。结构核查不是语义裁决，这里没有修改 gold。共同漏检应先复核题义与标签，再按模型当时已见线索做免费实验。

## 5. 建议的下一步顺序

1. **先做离线检索返回优化实验**：重放这 7 个真实查询及其当时上下文。优先检查限定名匹配/排序、函数实现与长 docstring 的首屏分配、宽泛查询结果多样性。固定查询、源码和字节预算，衡量目标正文是否进入首屏、返回字节和必要工具步数；不能以 gold 名称重写查询。保留当前版本作为对照。
2. **离线核查两道共同漏检**：复核 gold 与题义；分别从当时可见的 TABLE/解析线索、Resolver/列展开线索，比较普通搜索与图关系能否继续取得证据。只作排错开发，不能转称独立测试。
3. **之后才做同一 OpenHands 的有/无检索消融**：同一提示、基本工具、模型、源码、预算、收尾机会，仅检索工具可用性不同；固定题目与重复/顺序策略，另报请求和费用。当前原生 vs SDK 的全系统差异不能代替这个实验。

目前无需更换底座、强迫模型每题用检索或立刻扩大付费题量。本次仅分析已有轨迹、静态解析固定源码，未调用模型、未运行目标仓库代码、未改评分/检索/历史结果。
