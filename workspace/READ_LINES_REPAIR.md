# 共用读文件接口修复与检索选择假说

2026-11-13。两组共用的read_file已改为显式按行读取，并使用独立、不透明的续页游标。153项回归测试、SQLGlot两组真实SDK离线回放、三条批量模拟路径通过。本轮无真实模型请求、无费用、未读取凭据、未执行目标仓库代码。

## 新协议

首次调用可指定一基、包含端点的源码范围：

```json
{"path":"sqlglot/parser.py","start_line":5969,"end_line":5987}
```

省略范围则从首行读到文件末尾。start_line/end_line必须为正整数；超过文件范围、倒置范围或错误类型均拒绝，不静默截断/转换。
返回text逐行带原源码行号，并提供实际start_line/end_line、零基Unicode字符start_column/end_column（结束列不含该字符或行终止符）、total_lines及next_cursor。
返回列是源码行内位置，不是UTF-8字节位置，也不计行号前缀。展示统一CRLF/CR/LF为换行；行内Unicode不拆坏，U+2028/U+0085不会被错当物理源码换行。

续页：

```json
{"path":"sqlglot/parser.py","cursor":"复制上次返回的 next_cursor"}
```

续页可省略行范围，或保持与原查询相同的范围。cursor绑定当前会话、快照、文件、范围和位置；未签发游标、跨文件/会话或改范围均拒绝。
重复同一cursor在相同页容量下返回同一页，并正常计入调用/证据预算；不会隐藏推进位置。next_cursor=null表示本次请求范围结束，不一定是文件末尾。

新read_file schema和两个执行器均不接受offset，旧offset=5969不会被猜测转换为行号。普通搜索/文件清单/LocAgent保留原next_offset协议，系统说明分别注明两种协议。
用于核对历史账本的内部FileTools.render旧字符视图保留，但两个Agent执行器均经respond进入新LineReader，不能通过工具参数进入旧读取路径。

分页优先返回完整源码行；单行超过页预算时按Unicode字符分片，重复显示原行号并标明实际列范围，避免停滞或丢字。空文件返回空text、0总行数、null起止行/null续页；空行和末尾空行保留。
成功证据响应的完整JSON（含元数据、转义、UTF-8）计入4096字节/页与14,336字节总预算；放不下一个有效片段则关闭调查并保留终答机会。原有小型停机控制通知不是源码证据。

## 实现与隔离

- readonly_agent/read_lines.py：静态快照上的范围读取、原始行号/列号、已签发cursor与有界分页。
- core.py：共用schema、respond分派；search_text同步物理行号规则。
- openhands_tools.py：两组相同ReadAction及执行器，offset字段移除。
- openhands_replay.py：共用系统说明区分read_file.next_cursor和其他工具next_offset。
- LocBench活动离线夹具迁移到start_line；旧冻结夹具/原回包不修改，不能当作新协议直接重跑。

LocAgent实现与工具说明保持原样；没有同时做检索排序、描述或模型策略调整。

## 模型未选LocAgent：证据与可检验假说

证据基础仍是旧真实四组轨迹和已保存17组离线查询，见[上一轮诊断](LOCBENCH_OFFLINE_DIAGNOSIS.md)。本轮没有新增模型行为数据；下表的“假说”不是因果结论。

| 可检验假说 | 已有事实及限制 | 最小验证方法 |
|---|---|---|
| 已知文件时，read_file描述形成默认选择，模型没有意识到实体查询可直接取函数正文 | 两检索组都选择普通搜索/读取；说明建议已知文件用read_file。SQLGlot已有assignment函数名，该名字离线检索第1且正文1244字节。无法知道模型是否读懂或如何权衡描述 | 先保留当前检索描述运行修复后的共同读取基线；随后单独比较说明是否突出“已知符号直接取正文”，其余schema/预算不变，记录自主调用及正文进入下一请求 |
| 原问题词汇对当前ID索引缺乏帮助，检索不提供明显的首步发现优势 | Loguru标题仅Logger.add，traceback/RecursionError/recursion无候选；SQLGlot标题前5无目标，SetItem仅表达式类。索引不搜正文、BM25排除测试。这是能力证据，不能证明模型预知结果后拒绝工具 | 先离线固定题目短查询，比较现有ID索引与独立候选改进，记录目标rank/正文可见字节/空结果；oracle查询单列。不要只调工具宣传来掩盖覆盖不足 |
| 普通搜索已足以提供候选名称，额外检索的边际用途主要是证据读取 | SQLGlot两组均命中参考名称；直接实体读取可补正文，但原来基础read_file有共同缺陷 | 共用读取修复后比较关键正文覆盖、重复字节、总工具数及自主检索；检索优势必须超过修复后的正常基础工具，不能靠旧读取缺陷制造 |
| 固定三轮调查加一轮收尾，限制了纠错/尝试其他工具的机会 | 旧轨迹最后为finish，工具调用数/证据字节仍有余量；没有证据说模型下一轮一定会选检索 | 暂不同时扩大预算。之后若另做实验，两组同步增加相同调查机会并重新冻结；区分更多调查预算的效果与检索效果 |
| 大实体/整文件回包降低检索的效率 | 离线Logger.add约49KB、Loguru整文件约24KB，原预算无法读完目标；真实模型本轮没调用检索，故不能说这次是因看到大结果才放弃 | 独立离线比较短候选摘要/定点实体读取的预算利用率；不要把能力风险当作现有未选择的已证实原因 |

建议顺序：先确认新共享读取在真实模型上是否按行使用；再一次只改一个检索因素。自主调用率、有效证据进入下一请求、函数正文覆盖、定位/解释正确性、费用/耗时/失败应分开记录。强制调用只算连通性；旧题均已曝光，不能作为独立测试或宣称检索因果收益。

如果以后选择真实验证，新冻结入口仍为相同两题四组、最多16请求/34元保护上限；需要新批准与价格核查，本轮不启动，也不沿用旧授权。
