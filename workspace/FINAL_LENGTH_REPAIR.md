## 证据与原因边界

首题基础组最后一次真实请求只有 `finish` 工具，并指定调用它。真实回包函数名也是 `finish`；`finish_reason=length`、completion_tokens=1024，恰好达到请求的输出上限。参数共 4066 字符，包含尚未结束的长回答；JSON 没有闭合。原始终答未被接受、未评分，不能修补后算成功。

旧 schema 允许 `answer` 最多 4096 字符，另外还要输出最多五个文件、五个实体和 JSON 结构；整个响应却只有 1024 tokens。系统提示没有具体答案长度约束，收尾提示仅要求简洁且不超过输出限制。实际回答分多个长段落描述行为、并发与不确定性。已确认的直接失败原因是输出截断；格式容量与输出预算不协调是此次修复针对的设计问题。字符不等于 token，不能把 schema 上限理解为供应商保证能输出的长度，也不能证明模型为何选择写长文。

本次模型遵守了工具收尾选择；没有证据表明是旧 `read_file` 越界问题、工具混用或 SDK 吞掉了有效终答。原始请求/回包已提取为不含密钥和 HTTP 认证头的回归夹具；原账本不改动。

## 最小修复

- 正文 `answer` 从最多 4096 改为 **1200 字符**；wire schema 与两层终答校验使用同一常量，不截断或改写模型答案。
- 系统提示、工具 schema 描述、收尾提示均明确正文长度、简短句子、来源和不确定性，避免重复解释、代码引用及可选 summary。提示不含六题评分标准或题目专用提示。
- 整个响应上限从 1024 提高至 **2048 tokens**，为文件/实体及 JSON 留余量。SDK 限制、wire payload、usage 校验、独立 HTTP helper 固定参数和持久预算预留同步更新。
- 两组使用相同约束。每组仍最多 4 次请求，最后一次保留给 `finish`；没有增加补答、修复请求或自动重试。`length` 回包仍原样留证、结算已知 usage 后立即停止；完整但超长的答案也拒绝，不静默裁剪。
- 保留 v1 全部数据、rubric、源码、排序和 manifest；新方案另存 v2。新 live manifest 直接绑定完整重算的 base 内容，包含 runtime、数据、评分和驱动 hash；不会改写旧 manifest 或绕过绑定校验。新授权尚未创建。

1200 字符不是 token 数保证；多语言、长实体 ID、模型不遵守提示等仍可能造成拒绝或截断。离线验收证明接口和保护路径，不证明真实模型已经会稳定按新约束回答。
