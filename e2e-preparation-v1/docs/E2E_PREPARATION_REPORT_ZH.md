**A/B 的确切定义与预算**

B 的“当前定位”固定为最近 v7 基线：v6 标识符 BM25 与原源码预览，加 v7 自检提示和原终答。这里没有接入早期完整混合检索，也没有加入 dense、embedding、函数体检索或新重排。新题的基础提交源码通过适配器建索引；旧排名/预览/终答实现保留。新索引采用确定的路径顺序，不能声称与历史文件系统遍历顺序逐字节相同。详见 `docs/BASELINE_ADAPTER_ZH.md` 和 `config/frozen-baseline-source.json`。

A 输入 `{"issue":题面,"localization_packet":null}`；B 的同一字段承载定位器原终答及题目/基础提交元数据，不再生成新的定位总结。A/B 共用相同 Coding Agent、system prompt、工具定义、模型参数和编码预算；本地测试及真实 A/B 日志中的提示哈希、工具哈希和预算比较均一致。B 的定位预算及费用单列。

| 模型 | deepseek-flash；记录每个响应实际 model 字段 | 相同 |
| 温度、思考 | temperature=0；thinking disabled | 沿用冻结 wire 配置 |

预测 JSONL 包含 `instance_id`、`model_name_or_path`、`model_patch`。评测使用官方 [SWE-bench harness](https://www.swebench.com/SWE-bench/guides/evaluation/)，固定为兼容所选数据模式的 [v3.0.0 提交 d83e100](https://github.com/SWE-bench/SWE-bench/commit/d83e1001739f4d96add351d9ec0d56f4594a0d82)。阶段 1 设计里的较新提交要求不同的数据字段，本轮只修订新准备包中的 pin，历史冻结记录保持原样。评测启动包装器校验/复位基础提交；官方补丁应用、测试与评分逻辑未修改。

**发现的问题与处理**

1. 暂无云端主机：完成脚本和本地验证，将云端验收留待主机就绪。两张 amd64 镜像总未压缩标称大小约 8.17 GB，实际共享层占盘另计；最后检查无运行中的 Docker 容器，未删除既有镜像或执行全局清理。
2. 付费 v1 编码输出上限误设为 2,048，低于阶段 1 设计的 4,096，A 的长工具参数被截断。严格停止，不执行不完整工具调用。最终 v2 恢复 4,096，新增截断拒绝测试并通过 13 项离线回归；**v2 未再次付费测试**，不能宣称消除了所有截断风险。
3. B 真实运行重复诊断且未编辑：作为冒烟观察记录，不据此比较 A/B 效果，也不擅自改提示或定位方案。下一次需要验证非空补丁的完整路径。
4. 官方镜像最初 HEAD 与题目 base_commit 不同：付费前发现并修复，编码和评测启动均强制校验基础提交，模型侧删除历史。
5. harness 与数据模式、依赖版本冲突：固定兼容提交与 datasets/pyarrow/numpy/ghapi 等版本，在新目录重新建环境后 `pip check` 通过。最终归档检查还移除了 cloud lock 中从本地安装带入的 macOS NumPy wheel 路径，改为相同版本 `numpy==1.26.4`；静态检查确认云端锁文件无本机路径。Ubuntu 云端安装仍未运行。
6. 断点恢复：已完成步骤跳过；处于运行中、失败或代码/清单变更的状态拒绝自动重试。本次停止记录保持失败原样。将来改变预算必须创建新运行目录和新记录，不能拼接不同预算的 A/B 结果。
